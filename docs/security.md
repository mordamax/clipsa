# Security model

This document describes what Clipsa actually does to protect clipboard history and what it does not do.

## Threat model

**In scope:** protecting history at rest. A copied, synced or backed-up `clipboard.db`, a stolen disk image, or another user account must not reveal clipboard contents. Clipsa also avoids recording secrets in the first place where the OS makes that possible.

**Out of scope:** malware or another process running as your user while you are logged in. Such code can read the clipboard directly and can ask the OS keychain for Clipsa's key, subject to whatever prompts the OS shows. The optional app lock (Touch ID / login password on macOS, Windows Hello on Windows) only hides history in Clipsa's own windows after inactivity; it is a privacy screen against someone using your unlocked session, not encryption. While locked, capture continues and the history database stays readable by Clipsa's key as usual.

## Encryption

| Aspect | Implementation |
|---|---|
| Cipher | AES-256-GCM (`aes-gcm` crate); each item's content, preview and title are encrypted separately |
| Nonce | Random 96-bit nonce per encryption, stored with the ciphertext |
| What is encrypted | Item content (text, HTML and its plain-text alternative, PNG bytes, file path lists), the list preview (text excerpt or image thumbnail) and the optional item title |
| What is **not** encrypted | Content type, size, created/last-used timestamps, the pinned flag, the HMAC dedup tag, settings. The database itself is ordinary SQLite (no SQLCipher). |
| Master key | 256 random bits, created on first run, stored in the OS keychain via `keyring` 3: macOS Keychain, Windows Credential Manager, Linux Secret Service |
| Dedup | HMAC-SHA256 over the content, keyed with a sub-key derived from the master key via HKDF. No plain SHA hash of content is stored, so known content cannot be confirmed by hashing it. |
| Key material in memory | Key buffers use `zeroize` and are wiped on drop |
| Search | There is no plaintext index. A search decrypts matching-type items one at a time in memory, compares, and wipes each decrypted copy (`Zeroizing` / `ZeroizeOnDrop`). Image content is never loaded for search; images match by title only. Results carry only the decrypted preview (≤300 characters) and title, as the list always does. |

Items that fail to decrypt (for example, after a key change) are still listed with `readable: false` and an empty preview. They are never silently dropped.

### Keychain failure policy

If the keychain is unavailable or access is denied, Clipsa shows a dialog and exits. It does **not** generate a replacement key, because that would make all existing history permanently unreadable.

### Development builds

Debug builds use `<data dir>/clipsa-dev/` and a file-based key, so `pnpm tauri dev` never prompts for keychain access and never reads or writes release history. A file-based key offers no protection at rest. Never ship a debug build.

## Avoiding capture of secrets

- **Password-manager markers** (`ignore_sensitive`, on by default):
  - macOS: copies carrying `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType` are skipped.
  - Windows: copies carrying `ExcludeClipboardContentFromMonitorProcessing` or `Clipboard Viewer Ignore` are skipped.
- **Excluded apps:** copies made while an app listed in `excluded_apps` is frontmost are skipped. Use bundle ids on macOS and exe names on Windows; matching is case-insensitive.
- **Pause monitoring** from the tray or in Settings.
- **Linux:** neither marker detection nor frontmost-app detection is available. Pause monitoring, or delete sensitive items manually.

## Deletion and retention

- SQLite `secure_delete=ON` overwrites deleted content in the database file. Copies may still exist in filesystem snapshots, backups or SSD remapped blocks.
- `max_items` (oldest by last use are pruned) and `auto_cleanup_days` are enforced after every capture and once an hour.
- "Clear history" deletes all items.

## Network

The only network traffic is the update check (`check_for_updates`), which is off until the user opts in on the first-run screen or in Settings. It fetches `latest.json` from GitHub Releases. Update packages are verified against the minisign public key embedded in the app before they are installed. There is no telemetry, analytics or crash reporting.

## OS permissions

- macOS **Accessibility** is needed only for `paste_item` (simulating Cmd+V into another app). Capturing does not need it. The Mac App Store edition does not paste and never asks for it.
- The global hotkey and launch at login use the standard Tauri plugins; the Mac App Store edition uses macOS Login Items (`SMAppService`) instead of the autostart plugin.

## Reporting vulnerabilities

Use [GitHub private security advisories](https://github.com/mordamax/clipsa/security/advisories/new). Please do not open public issues for vulnerabilities.
