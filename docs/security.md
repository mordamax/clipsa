# Security model

This document describes what Clipsa actually does to protect clipboard history and what it does not do.

## Threat model

**In scope:** protecting history at rest. A copied, synced or backed-up `clipboard.db`, a stolen disk image, or another user account must not reveal clipboard contents. Clipsa also avoids recording secrets in the first place where the OS makes that possible.

**Out of scope:** malware or another process running as your user while you are logged in. Such code can read the clipboard directly and can ask the OS keychain for Clipsa's key, subject to whatever prompts the OS shows. The optional app lock (Touch ID / login password on macOS, Windows Hello on Windows) only hides history in Clipsa's own windows after inactivity; it is a privacy screen against someone using your unlocked session, not encryption. While locked, capture continues and the history database stays readable by Clipsa's key as usual.

## Encryption

| Aspect | Implementation |
|---|---|
| Cipher | AES-256-GCM (`aes-gcm` crate); each item's content, preview and title are encrypted separately |
| Nonce | Random 96-bit nonce per encryption, stored with the ciphertext |
| What is encrypted | Item content (text, HTML and its plain-text alternative, PNG bytes, file path lists), the list preview (text excerpt or image thumbnail) and the optional item title |
| What is **not** encrypted | Content type, size, created/last-used timestamps, the pinned flag, the HMAC dedup tag, settings. The database itself is ordinary SQLite (no SQLCipher). |
| Master key | 256 random bits, created when the user completes the first-run screen (which explains the keychain first; nothing is captured before). Direct download: stored via `keyring` 3 in the macOS login keychain, Windows Credential Manager or Linux Secret Service, service `clipsa`, account `encryption_key`. Mac App Store edition: stored in the macOS data protection keychain (service `clipsa-app-store`), which only that app's keychain access group can read, so macOS never asks the user for access. It is readable once the Mac has been unlocked after starting (`kSecAttrAccessibleAfterFirstUnlock`), also while the screen is locked, so Clipsa can start then, e.g. after an automatic update; keys stored by 0.1.5 are switched to this the next time they are read. |
| Dedup | HMAC-SHA256 over the content, keyed with a sub-key derived from the master key via HKDF. No plain SHA hash of content is stored, so known content cannot be confirmed by hashing it. |
| Key material in memory | Key buffers use `zeroize` and are wiped on drop |
| Search | There is no plaintext index. A search decrypts matching-type items one at a time in memory, compares, and wipes each decrypted copy (`Zeroizing` / `ZeroizeOnDrop`). Image content is never loaded for search; images match by title only. Results carry only the decrypted preview (≤300 characters) and title, as the list always does. |

Items that fail to decrypt (for example, after a key change) are still listed with `readable: false` and an empty preview. They are never silently dropped.

### Keychain failure policy

Clipsa never generates a replacement key when the keychain is unavailable or access is denied, because that would make all existing history permanently unreadable. On first run, the first-run screen shows the error and a **Try again** button; nothing has been saved yet. Later starts show a dialog with **Try Again** and **Quit**, except when the keychain is only locked because the Mac hasn't been unlocked since it started (Mac App Store edition): then Clipsa waits and loads the key as soon as the Mac is unlocked.

### Development builds

Debug builds use `<data dir>/clipsa-dev/` and a file-based key, so `pnpm tauri dev` never prompts for keychain access and never reads or writes release history. A file-based key offers no protection at rest. Never ship a debug build.

## Avoiding capture of secrets

- **Password-manager markers** (`ignore_sensitive`, on by default):
  - macOS: copies carrying `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType` are skipped.
  - Windows: copies carrying `ExcludeClipboardContentFromMonitorProcessing` or `Clipboard Viewer Ignore` are skipped.
- **Excluded apps:** copies made while an app listed in `excluded_apps` is frontmost are skipped. Use bundle ids on macOS and exe names on Windows; matching is case-insensitive.
- **Pause monitoring** from the tray or in Settings.
- **Linux:** neither marker detection nor frontmost-app detection is available. Pause monitoring, or delete sensitive items manually.

## Deletion and retention

- SQLite `secure_delete=ON` overwrites deleted content in the database file. Copies may still exist in filesystem snapshots, backups or SSD remapped blocks.
- `max_items` (oldest by last use are pruned) and `auto_cleanup_days` are enforced after every capture and once an hour.
- "Clear history" deletes all items.

## Network

The only network traffic is the update check (`check_for_updates`), which is off until the user opts in on the first-run screen or in Settings. It fetches `latest.json` from GitHub Releases. Update packages are verified against the minisign public key embedded in the app before they are installed. There is no telemetry, analytics or crash reporting.

## OS permissions

- macOS **Accessibility** is needed only for `paste_item` (simulating Cmd+V into another app). Capturing does not need it. The Mac App Store edition does not paste and never asks for it.
- The global hotkey uses the standard Tauri plugin. Launch at login writes a LaunchAgent (macOS), a `Run` registry value (Windows) or an XDG autostart entry (Linux) through `auto-launch`; the Mac App Store edition uses macOS Login Items (`SMAppService`) instead.

## Release pipeline

The repository is public and the release workflow holds keys that could ship code to every Clipsa user: the updater signing key (any update signed with it installs silently once published), the Developer ID certificate and notarization key, and the Homebrew tap credential. The measures below limit who and what can reach them.

**Who can run code with the secrets**
- All release secrets live in the GitHub environment `release`, which only accepts jobs running from version tags (`v*.*.*`); App Store secrets live in `appstore`, which only accepts `master` and version tags and holds each run until the maintainer approves it, so not even a malicious merge can use the App Store keys unnoticed. The release PR bot (`release-pr.yml`) uses environment `release-pr` (`master` only), which holds only the GitHub App's key; its tokens are limited to this repository's contents and pull requests and expire after an hour. It can open the release PR and create a version tag, but a tag is only created for a version whose dated changelog section is on `master`, which takes the maintainer merging the release PR. There are no repository-level secrets, so branch and pull-request workflows see none.
- Workflows from forks never receive secrets, and every outside contributor's first workflow run needs the maintainer's approval. No workflow uses `pull_request_target`.
- Website PR previews need the Cloudflare token, which can also deploy clipsa.dev. The PR's code never runs with it: `site-preview-build.yml` packs `site/` with no secrets, and `site-preview.yml` runs from `master` (`workflow_run`, environment `site-preview`, which only accepts `master`), installs wrangler from master's lockfile and uploads only those static files, refusing `_worker.js` and `_routes.json`. PRs from forks get no preview.
- The default `GITHUB_TOKEN` is read-only; only the jobs that create or publish the release get `contents: write`. `actions/checkout` runs with `persist-credentials: false`, so build scripts of dependencies can't pick the token up from `.git/config`.
- Secrets and inputs reach scripts through environment variables, never through `${{ }}` text substitution into shell code.

**What code runs**
- Every action is pinned to a full commit SHA, the repository requires SHA pinning, and only GitHub-owned actions plus `tauri-apps/tauri-action`, `dtolnay/rust-toolchain`, `Swatinem/rust-cache`, `pnpm/action-setup`, `ossf/scorecard-action` and, for Windows signing, `signpath/github-action-submit-signing-request` are allowed. Dependabot proposes updates to the pins.
- Dependencies install from the committed lockfiles (`pnpm install --frozen-lockfile`, `Cargo.lock`). Release and App Store builds use no caches, so nothing written by an earlier run can leak into a signed build.
- Dependabot alerts, Dependabot security updates, secret scanning and push protection are enabled.

**What can change after the fact**
- `master` can't be force-pushed or deleted, and `v*` tags can't be moved or deleted (repository rulesets, no bypass). The tap's `main` branch has the same branch rule.
- Releases are immutable once published, so assets such as `latest.json`, the DMGs and the updater bundles can't be swapped later.
- The release and App Store workflows refuse to run when the tag doesn't match the app version.
- Every installer the website links to has a signed build provenance attestation (`actions/attest-build-provenance`, over the files in `SHA256SUMS`). `gh attestation verify <file> -R mordamax/clipsa` checks that the file was built by `release.yml` in this repository from its version tag.
- [OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/mordamax/clipsa) checks these practices every week (`scorecard.yml`) and publishes the result; its findings also appear in the repository's code scanning alerts.

**Credential scope**
- Notarization uses an App Store Connect API key with the Developer role, which can't read the Apple ID's iCloud data the way an app-specific password can.
- The Homebrew tap and the release PR bot use one-hour tokens minted from the clipsa-release-bot GitHub App, installed on `mordamax/homebrew-tap` and `mordamax/clipsa` with Contents and Pull requests: write. Each job asks only for the repository and permissions it needs (the tap: its contents; the release PR: this repository's contents and pull requests). The App's private key is stored in two environments, `release` (tags only) and `release-pr` (`master` only); a leak of it could push to the tap or open PRs and create tags here, so it is rotated like the other keys below.
- Windows signing uses a SignPath API token with the submitter role, stored in `release`. It can only submit artifacts uploaded by a GitHub-hosted run of this repository's workflows, and SignPath doesn't sign anything until the request is approved there by hand. The signing key itself stays in SignPath's HSM.

**If a key leaks:** revoke the Developer ID certificate (developer.apple.com → Certificates) and the API key (App Store Connect → Users and Access → Integrations), regenerate the GitHub App's private key, revoke the SignPath API token, and rotate the updater key by publishing one last update signed with the old key that carries the new public key.

## Reporting vulnerabilities

Use [GitHub private security advisories](https://github.com/mordamax/clipsa/security/advisories/new). Please do not open public issues for vulnerabilities.

Reports get a first response within 14 days. Confirmed vulnerabilities are fixed in a release, and its release notes list them under **Security**.
